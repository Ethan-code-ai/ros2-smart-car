## 1. 项目来源与团队协作

本项目由团队协作开发，展示仓库 [Ethan-code-ai/ros2-smart-car](https://github.com/Ethan-code-ai/ros2-smart-car) 基于 [xbai55/ros2-smart-car](https://github.com/xbai55/ros2-smart-car) 继续整理，保留既有 Git 提交历史、课程总结报告、工程实现及后续迭代内容。

**报告分工**：梁家齐负责系统架构、ROS2 上层控制、Web 前后端、YOLO11/ByteTrack/HSV 感知集成、交通灯数据与微调部署，以及系统联调。完整团队分工与阶段成果见[总结报告](reports/项目II总结报告.md)，代码演进可结合 Git 历史阅读。

工程运行在 Yahboom ROSMASTER X3 麦克纳姆轮底盘与 Jetson 上，使用 ROS2 Humble。厂商提供底盘/雷达驱动及 URDF 等基础能力；检测、跟踪和建图分别采用 Ultralytics YOLO11、ByteTrack 和 slam_toolbox。PP-Human 是保留的历史离线对照，STM32 模块使用 HAL。项目中的开发内容主要是感知节点封装、目标选择与业务规则、运动安全仲裁、Web 服务与界面、设备资源管理、部署和评测工具，不将第三方算法或厂商驱动描述为完全自研。

可用于项目简介的表述：

> 基于 ROS2 Humble、Jetson 与麦克纳姆轮底盘构建智能小车感知和控制系统，集成多模式安全仲裁、YOLO11/ByteTrack 人物目标锁定、HSV 颜色追踪及 FastAPI/React 实时控制台；完成底盘、感知、网页控制和安全停车链路的阶段实车验证，并建立人员异常检测离线评测及 STM32 传感器采集模块。SLAM 建图和连续人物跟随仍在推进实车验收。

## 2. ROS2 与 Web 工程完整进展

### 2.1 底盘接入与模式决策

本项目功能包位于 [`ros2_ws/src/smart_car_decision/`](../ros2_ws/src/smart_car_decision/)。统一启动文件接入厂商 `Mcnamu_driver_X3`、SLLidar、底盘里程计与机器人 TF，并启动模式管理、决策控制、雷达监视、YOLO、颜色追踪、人物跟随、状态汇总、Web 和 TCP 桥接节点。

支持 `stop`、`manual`、`auto`、`color_track`、`object_follow`、`mapping`、`navigation` 七种模式。其中 `navigation` 目前输出零速度，尚未接入 Nav2 完整目标导航；模式名称存在不代表导航已经完成。网页或旧 TCP 工具的手动指令先进入统一控制器，再发布最终 `/cmd_vel`。

急停优先级最高；手动指令超过 0.7 秒未刷新、人物或颜色偏移超过 0.5 秒失效时停车。`auto`、颜色追踪、人物跟随和建图模式还检查 0.6 秒雷达超时。近障停车阈值按模式配置：当前自动、颜色与人物跟随默认 0.45 m；`manual`、`mapping` 默认 0，表示未启用近障强制停车。不能将“安全控制已实现”解释为所有模式都会自动避开障碍。

代码入口：[控制策略](../ros2_ws/src/smart_car_decision/smart_car_decision/control_policy.py)、[控制节点](../ros2_ws/src/smart_car_decision/smart_car_decision/decision_controller.py)、[模式节点](../ros2_ws/src/smart_car_decision/smart_car_decision/mode_manager.py)、[参数](../ros2_ws/src/smart_car_decision/config/decision.yaml)。

### 2.2 激光雷达与运行健康

从原始 `/scan` 过滤非有限值和量程外距离，在车头中心 180°、左右各 35° 的扇区内计算 20% 低分位距离，减少单个异常近点的影响。网页点云按安装方向旋转并降采样，显示点仅用于可视化，原始扫描用于控制和建图。

状态链路提供扫描年龄、频率、有效点比例、frame、里程计、TF、最终速度和地图健康检查。历史实车记录中扫描约 7–10 Hz，并修复了前方距离为空及网页车头方向不一致的问题；更换雷达安装方向后需要重新检查参数。

代码入口：[雷达数据处理](../ros2_ws/src/smart_car_decision/smart_car_decision/scan_visualization.py)、[雷达健康](../ros2_ws/src/smart_car_decision/smart_car_decision/lidar_health.py)、[状态汇总](../ros2_ws/src/smart_car_decision/smart_car_decision/system_status_node.py)。

### 2.3 YOLO11、人物目标选择与颜色追踪

默认 YOLO 模型仍是 `yolo11s.pt`。`auto` 模式将停车标志、行人/车辆和交通灯结果转换成高层指令；交通灯目前仍采用通用框加 HSV 颜色辅助判断。遮挡画面停车、安全指令保持和识别超时处理位于视觉与控制逻辑中。

`object_follow` 已接入 Ultralytics ByteTrack，只选择 `person` 作为跟随对象。支持自动选择、按 `track_id` 锁定、网页点选和恢复自动选择。自动目标丢失后可重选，手动选定的目标丢失后等待，避免直接改跟旁人；没有 ID 的兼容输入保留中心距离回退。当前 `track_buffer=30` 帧，选择器的 0.8 秒丢失超时是另一项参数。它不提供人脸识别或 ReID，不能保证长期遮挡后的身份一致性。

HSV 颜色追踪支持红、绿、蓝、黄预设、自定义阈值、质心偏移和标注帧。配置经 REST/ROS 话题在线更新，并保存到浏览器 `localStorage`；刷新后重新下发。清除浏览器数据或更换终端后仍会回到后端默认值，尚未实现 Jetson 端共享持久化。

相机按模式分配：非视觉模式由 Web 直接预览，自动/人物模式由 YOLO 占用，颜色模式由颜色节点占用；Web 转发标注 JPEG，避免同时打开 `/dev/video0`。颜色节点请求 MJPG、1280×720、30 FPS；这是采集配置，不能当作已测得的推理帧率。

历史人物链路实测包含约 9.6–10.2 FPS 标注帧、偏移发布/转发、近障条件下最终速度为零。测试时近障阻止车辆前进，因此当前 ByteTrack 版本的连续移动、转向、遮挡和多人交叉仍待现场验收。

代码入口：[YOLO 节点](../ros2_ws/src/smart_car_decision/smart_car_decision/yolo11_camera_node.py)、[目标选择](../ros2_ws/src/smart_car_decision/smart_car_decision/person_target.py)、[颜色节点](../ros2_ws/src/smart_car_decision/smart_car_decision/color_tracker_node.py)、[ByteTrack 参数](../ros2_ws/src/smart_car_decision/config/bytetrack.yaml)。

### 2.4 Web 控制台与地图工程

React/TypeScript/Vite 前端已通过真实 REST/WebSocket 接口连接 FastAPI/ROS2 后端。功能包含模式切换、急停、速度与手动方向控制、HSV 配置、人物目标点选、视频、雷达、状态/原始 JSON、地图快照与位姿显示、地图保存和建图重启。`useRobotState` 会获取状态快照并建立状态 WebSocket，断线后重连；初始化默认值不代表模拟机器人数据。

建图部分已有 slam_toolbox 参数与 launch、前提检查、rosbag2 录制/回放、地图保存/检查/加载、元数据和质量报告工具。Web 地图显示、降噪和位姿平滑也已有代码。当前仍缺 Jetson 现场的 TF/里程计核验、闭环地图、两次独立建图质量对比和重启加载证据，不能称为已完成 SLAM 实车验收，更不能称为已完成自主导航。

当前 bringup 默认发布 `base_link → laser` 静态 TF，mapping launch 还留有默认关闭的额外静态 TF 选项。现场必须确认唯一发布者、frame 和实测安装位姿，避免同一关系重复发布。

代码入口：[Web 后端](../ros2_ws/src/smart_car_decision/smart_car_decision/web_app_node.py)、[前端状态与请求](../web-console/src/useRobotState.ts)、[前端说明](../web-console/README.md)、[建图启动](../ros2_ws/src/smart_car_decision/launch/mapping.launch.py)、[地图资产](../ros2_ws/src/smart_car_decision/smart_car_decision/map_assets.py)、[地图规范](../maps/README.md)。

### 3.2 当前躺卧即时告警

当前入口 [`demo/yolo11_fall_demo.py`](../demo/yolo11_fall_demo.py) 保留通用 YOLO11 输出，另用跌倒专用权重识别 `fallen/sitting/standing`。`fallen` 置信度达到 0.25 时当帧告警，不等待 2 秒、不要求跟踪 ID，不加载飞桨运行时；通用模型不会作为告警门槛。

支持本地视频/摄像头、场景开始/结束事件、异步系统提示音、证据截图、逐帧 JSONL、环境/模型哈希、运行摘要和可选标注视频。窗口支持暂停、前后逐帧回看及结束后继续检查；回看缓存不重复推理或报警。声音请求有代码与静音测试记录，实际可听输出不作为已验收结果。

这是 **Windows/CUDA 独立 Demo**，尚未连接 ROS2 告警话题、网页告警页、机器人制动或 MQ2 模块。识别“躺卧”也不等于判断跌倒原因或人员健康状况。

## 4. STM32 MQ2/OLED 独立模块

[`src/mq2/`](../src/mq2/)提供 STM32F103C8T6 固件、构建/烧录脚本与只读串口监视器。PA0 读取 ADC，I2C1 驱动 OLED，USART1 以 115200 波特率输出原始值和估算 A0 电压，每 500 ms 更新；OLED 通信失败时继续采集，并尝试恢复。

2026-10-14 的记录包含原 Flash 备份、烧录回读验证、真实串口读数及 OLED 地址 0x3C，用户已确认屏幕显示。OLED 版本记录占用 Flash 9,432 字节、RAM 3,304 字节。历史验证时 MQ2 使用原有 3 V 供电，只能证明采集和通信工作；正式灵敏度验证还需确认加热供电、分压及最终接线。

屏幕明确显示 `PPM: NOT CAL`。尚未进行 ppm 标定、烟雾报警阈值验证或与 ROS2 联动，不能将原始 ADC 换称浓度。接线、构建与硬件记录见[模块 README](../src/mq2/README.md)。

## 5. 运行与复现入口

### 5.1 Jetson 原生工程

前提为目标 Jetson 已配置 ROS2 Humble、厂商底盘/雷达/描述包、相机及匹配的视觉依赖。仓库不包含完整厂商工作空间。检查串口映射、相机编号、雷达方向及 [`decision.yaml`](../ros2_ws/src/smart_car_decision/config/decision.yaml) 中的静态资源路径后运行：

```bash
cd ~/ros2-smart-car
bash scripts/build_jetson.sh
bash scripts/run_jetson.sh
```

Web 服务默认端口 8080，通过 `http://<Jetson-IP>:8080` 访问。系统默认 `stop`。前端首次部署需先执行 `web-console` 的 `npm ci` 与 `npm run build`，并保证 `static_dir` 指向该机器实际的 `web-console/dist`；仓库当前路径值不能直接套用到所有用户名。

```bash
export ROS_DOMAIN_ID=77
ros2 node list
ros2 topic echo /robot/status
ros2 topic echo /cmd_vel
ros2 topic hz /scan
ros2 topic hz /vision/annotated_frame
bash scripts/check_mapping_prereqs.sh
ros2 launch smart_car_decision mapping.launch.py
```

地图录制、保存、检查与加载命令见[首页构建与运行](../README.md#10-构建与运行)。现场先核对 TF 唯一性与安装参数，建图和导航验收需要额外实车证据。Docker 文件已保留，但本次未完成容器环境实车验收。

### 5.2 最新躺卧 Demo 与评测

Windows 本地需要 CUDA 可用的 PyTorch、Ultralytics、OpenCV 和通用/跌倒两套权重。当前程序显式要求 CUDA，不会自动回退 CPU。已验证的本机软件环境见下一节；其他机器需先安装匹配显卡/驱动的依赖。

```powershell
# 从仓库根目录运行；替换为自己的视频文件。
& '.\.venv-demo\Scripts\python.exe' '.\demo\yolo11_fall_demo.py' --source 'C:\videos\demo.mp4' --save-video --start-paused
& '.\.venv-demo\Scripts\python.exe' '.\demo\yolo11_fall_demo.py' --source 0

# 准备好 URFD 压缩包后，推理并评测全部本地序列。
& '.\.venv-demo\Scripts\python.exe' '.\demo\eval_yolo11_fall.py' all --scope all --dataset-dir 'C:\datasets\URFD' --skip-videos

# 已有匹配推理缓存时，仅重放计分。
& '.\.venv-demo\Scripts\python.exe' '.\demo\eval_yolo11_fall.py' evaluate --scope all --dataset-dir 'C:\datasets\URFD'
```

新机器不能仅凭 Git 中的报告执行缓存重放：URFD 原始数据、`.urfall-work` 推理缓存、虚拟环境和完整 `demo_output` 临时输出未打包，需要另行准备数据并先生成缓存。两次双模型运行的视频、截图和逐帧记录已单独归档到 [demo/validation](../demo/validation/README.md)。`--scope all` 与 `--confirm-seconds 0` 是当前全量即时策略；可通过 `--out-dir` 指定新目录保存实验结果。运行快捷键、生成物和限制见[本地运行说明](YOLO11躺卧即时告警-本地运行.md)。

历史规则入口是 `demo/person_anomaly_demo.py`，包含长时间停留、疑似倒地、事件优先级和通道占用接口；真实地图通道占用必须由外部地图监视器提供，独立视频不能代替地图判断。PP-Human 历史运行另需隔离环境及模型，见[飞桨本地测试](飞桨跌倒检测-本地测试.md)。
