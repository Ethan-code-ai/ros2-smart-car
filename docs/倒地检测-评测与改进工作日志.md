## 2. 评测框架

新建 `demo/eval_urfall.py` + `demo/urfall/` 包。**核心设计：把昂贵的 GPU 推理和廉价的规则回放彻底解耦**——GPU 只跑一遍，每帧检测结果缓存成 JSON；之后的计分、阈值扫描、交叉验证都是纯 Python 重放，可以反复跑。

```
demo/eval_urfall.py          CLI 入口（prepare / detect / evaluate / bench / all / selftest）
demo/urfall/dataset.py       解压、下载解析官方标注、枚举帧
demo/urfall/detect.py        GPU 推理 + 检测缓存读写（唯一 import torch/ultralytics 的模块）
demo/urfall/replay.py        AnomalyEngine 重放 → 逐帧告警信号
demo/urfall/metrics.py       混淆矩阵、事件级指标、召回上限、阈值扫描、交叉验证
demo/urfall/report.py        Markdown / JSON / JSONL / 失败帧
demo/urfall/compare.py       五种倒地判据 A/B 对比
demo/urfall/evidence.py      改进前后 / 跌倒 vs 主动躺下 的对比截图
demo/urfall/event_metrics.py 事件级指标 CLI
demo/urfall/diagnose.py      单段逐帧诊断（最快的定位工具）
tests/test_eval_urfall.py    55 个单测，不需要 GPU / 数据集 / 网络
```

### 数据与标注

- 数据：`D:\智能小车\dataset\*.zip`，URFD cam0 RGB，每段一个 zip，内含 `<seq>-cam0-rgb-NNN.png`，640×480，30 fps。
- 标注：程序自动从 `http://fenix.ur.edu.pl/~mkepski/ds/data/urfall-cam0-{falls,adls}.csv` 下载并缓存。无表头，列 0=序列名、列 1=帧号（1-indexed，与 PNG 文件名一致）、列 2=标签。
- 标签含义：`-1` 未躺地、`0` 过渡态、`1` 躺地。**标注只描述姿态，不描述意图**——这一点后来成了关键（见第 5 节）。

### 几个必须记住的实现细节

1. **时间轴**：`now = (frame_number - 1) / 30.0`。
2. **跟踪器重置**：每段之间调用 `tracker.reset()`（沿用 `yolo11_camera_node.py:420` 的写法）并额外 `BaseTrack.reset_id()`，让 track ID 从 1 开始，缓存可复现可 diff。
3. **缓存键**：`CacheKey`（model/tracker 的 sha1、imgsz、conf、device、batch、版本号）做摘要，`evaluate` 阶段摘要不一致直接报错，不静默混用。
4. **YOLO 置信度分层**：缓存阶段用 `--yolo-conf 0.1`（对齐 ByteTrack 的 `track_low_thresh`）存超集，回放时由 `AnomalyEngine` 按 `confidence` 过滤，这样 `confidence` 也可扫描。
5. **批处理与 persist=True 是兼容的**（查 `ultralytics/trackers/track.py`：list 输入时 `dataset.mode != "stream"`，只建一个 tracker，批内结果仍按顺序逐帧喂给 `tracker.update()`）。但默认仍用 `--batch 1` 与生产节点保持一致。

### 踩到的两个坑（都已修）

**OpenCV 非 ASCII 路径**：项目路径含 `智能小车`，OpenCV 5.0 的 `cv2.imread` 走窄字符 C API，**静默返回 None**。`detect` 阶段能跑通只是因为 import ultralytics 会 monkey-patch `cv2.imread`；计分路径没 import ultralytics 就暴露了。已在 `detect.py` 写 `imread_unicode` / `imwrite_unicode`（`np.fromfile` + `cv2.imdecode`），不依赖那个 patch。

**浮点时间戳导致去抖偶尔晚一帧**：`145/30 - 100/30 = 1.4999999999999996 < 1.5`，告警比理想算术晚 1 帧（33 ms）。已写测试钉住，不值得改规则。

## 3. 第一轮：10 段子集（结论已被推翻，保留用于对照）

当时 `dataset/` 只有 10 段（fall-01~05 + adl-01~05），1386 个可评测帧，5 个跌倒事件。

### 3.1 初始状态：一次告警都没触发

默认参数（`fall_ratio=1.1`, `fall_seconds=1.5`）下 **TP=0**。不是表现好，是规则完全没生效。

根因**不是阈值，是人员检测**：

| 真实姿态 | yolo11s 检出率 |
|---|---:|
| 站立 | 99.7% |
| **躺地** | **32.3%** |

人完全躺在地上之后 YOLO11s 经常**根本检不到人**（连续 25 帧以上无框，人还完整可见）。COCO 的 person 类以站立姿态为主，卧姿是分布外样本。没有人员框，宽高比规则无从判断。

**被证伪的便宜招**：放宽置信度门限对此无效——conf 从 0.35 降到 0.10，躺地检出率只从 32.3% 升到 36.3%。模型不是给出低分框，而是**根本不出框**。

### 3.2 换姿态模型

| 模型 | 躺地检出 | 站立检出 | ghost 帧 | 纯模型速度 |
|---|---:|---:|---:|---:|
| yolo11s | 32.3% | 99.7% | 0 | 144.9 fps |
| **yolo11s-pose** | **65.9%** | 99.8% | 0 | 101.0 fps |
| yolov8s-pose | 74.0% | 100.0% | 3 | 124.9 fps |

选 `yolo11s-pose`：比 yolov8s-pose 低 8 个点检出率但 ghost 帧为 0，端到端 F1 只差 0.007。

### 3.3 开源方案调研

- [mfarchan-arm/Fall-Detection](https://github.com/mfarchan-arm/Fall-Detection) —— 用 **stock 姿态权重 + 跟踪/状态机逻辑**，不训练模型。在 UR Fall 上报 26/30 跌倒、1/40 误报。它独立验证了我的测量（报 yolov8s-pose 躺地召回 70% vs yolo11s-pose 58%，我测 74.0% vs 65.9%，同样排序同样约 12 点差距）。**但仓库无 LICENSE，代码不能直接移植**，只能参考思路。
- [SyedBurhanAhmed/Real-Time-Fall-Detection-using-YOLO](https://github.com/SyedBurhanAhmed/Real-Time-Fall-Detection-using-YOLO) —— MIT 许可、有 IEEE 论文，但权重实际下载不到，指标只有「95% accuracy」无测试协议。
- ultralytics 及其权重是 **AGPL-3.0**，课程/研究用没问题，商用需 Enterprise License。

值得照搬的**思路**（非代码）：两级置信度门限、落地区重绑定、告警在轨迹丢失后保持、tentative track 抑制误检、**状态机区分「快速下降后躺地」和「缓慢躺下」**。最后一条是关键，见第 5 节。

### 3.4 躯干角实验 —— 与预期相反，更差

用 17 个 COCO 关键点算肩中点→髋中点与垂直方向的夹角，理论上更抗截断和视角变化。**实测明显更差**（同一批缓存检测，五种判据各自调优后）：

| 判据 | 调优后 F1 | 交叉验证样本外 F1 |
|---|---:|---:|
| **宽高比** | **0.791** | **0.779** |
| 任一满足 | 0.758 | 0.747 |
| 同时满足 | 0.632 | 0.632 |
| 躯干角优先 | 0.142 | 0.042 |
| 躯干角（无回退） | 找不到零误报配置 | — |

两个原因：
1. **覆盖更低**：223 个躺地帧里只有 91 帧能同时拿到可信的肩和髋，而有外框的是 147 帧。
2. **透视缩短**：人躺着时身体长轴常朝向摄像头，肩髋连线在画面里又短又接近竖直，而四肢摊开仍让外框变宽。

→ 默认 `fall_feature_mode` 保持 `bbox`。关键点能力完整保留在代码里，**换到低视角的小车摄像头后值得重测**（那里外框透视畸变更严重，结论可能反转）。

### 3.5 消融：两级门限没改变结果

`track_confidence=0.15` 让已确认轨迹靠弱检测续命，躺地检出率 65.9% → 71.7%。但消融显示它、冷却时长、丢失宽限三者对最终 TP/FP **一个都没改变**。保留是因为零成本且更稳健，不是因为在这批数据上有效。

| | 改进前 | 改进后 |
|---|---:|---:|

| 跌倒报出 | 0/5 | 4/5 |
| 日常活动误报 | 0/5 | 0/5 |
| 帧级精确率 | 未定义 | 100% |
| 交叉验证样本外 F1 | — | 0.779 |

## 4. 中途修正的两个方法学问题

### 4.1 帧级召回率不是主指标（用户指出）

帧级召回率把「人躺着的每一帧都要持续报警」当成要求，但巡逻场景**每次跌倒报一次就够**。

关键是把漏检按**后果**拆开：

| 类型 | 运营影响 |
|---|---|
| **报警前延迟** | 无 —— 去抖+检测延迟，报一次就够 |
| **报警后掉线** | 真缺陷 —— 消费方会以为人已经起来了 |

实测（两轮都成立）：**报警后掉线 0 帧，报警后覆盖率 100%**。告警一旦拉起就稳定保持到最后。所以帧级召回率衡量的几乎全是去抖窗口，不是检测失败。

已把报告结构改为**第 3 节事件级（主指标）、第 4 节帧级（次要，用于诊断）**。

### 4.2 计分口径自相矛盾（扩充数据后暴露）

帧级把所有 `label=1` 当正样本（包括 ADL 里主动躺下的 1470 帧），事件级却把 ADL 报警算误报。现在显式分两种口径：

- **`fall_only`（主口径）**：只有跌倒段的躺地帧算正样本，日常段主动躺下算负样本，在那报警 = 误报。
- **`any_lying`**：只问「能不能看出有人躺着」，不问是不是跌倒。

两者差距就是「摔倒」和「自己躺下」区分不开的代价。

## 5. 第二轮：全量 69 段 —— 结论被推翻

数据集扩充到 **69 段 / 11756 帧 / 9654 个可评测帧 / 30 个跌倒事件**（缺 adl-08）。

| | 10 段子集 | **69 段全量** |
|---|---:|---:|
| 跌倒报出 | 4/5（80%） | **16/30（53%）** |
| 误报段数 | 0/5 | **14/39** |
| 误报帧 | 0 | **855 帧（175.7 帧/分钟）** |
| 帧级精确率 | 100% | **39.6%** |
| 交叉验证样本外 F1 | 0.779 | **0.320** |

### 根本原因：静态姿态判据原理上分不开「摔倒」和「自己躺下」

URFD 的日常活动段里有 **16 段是人主动躺在地板或床上**，标注与真跌倒完全相同。规则在其中 **13 段误报**；而没有躺下动作的 23 段只误报 1 段。

**不是阈值松的问题。** 零误报调参会塌掉——推荐参数被推到扫描上界 `fall_ratio=1.8`，召回只剩 17.9%，等于不报警。改阈值只会在「漏报」和「误报」之间平移。

截图证据（`demo/results-urfall/evidence/`）：

- `混淆-fall-08f078-vs-adl-31f146.jpg` —— 左真跌倒 `ratio=1.85 角度=83°`，右主动躺地 `ratio=1.32 角度=75°`，都报警，数值和画面几乎一样。
- `混淆-fall-02f095-vs-adl-36f299.jpg` —— 右边躺在**床上**，`ratio=1.17`，照样报警。
- `混淆-fall-16f054-vs-adl-11f258.jpg`、`混淆-fall-20f089-vs-adl-10f267.jpg`

### 扩充后依然成立的结论

- 报警后掉线 **0 帧**，报警后覆盖率 **100%**。
- 跌倒段的 414 个帧级漏检**全部**是报警前延迟。告警延迟中位 9 帧、最大 20 帧（0.67 秒）。
- 瓶颈仍在检测覆盖：躺地帧检出率 71.7%，站立 99.8%。

### 本轮修掉的两个框架缺陷

1. **误报被系统性低估**：`event_level` 原先只把「没有躺地标注」的 ADL 段计入误报，导致 16 段难负样本全被豁免——曾报告「误报 1/39 段」，实际 **14/39 段**。已加回归测试。
2. **交叉验证跑不动**：原为逐段留一法，69 段时要跑 69 次全量扫描。改为分组 k 折（`--loso-folds`，默认 10），序列轮流分配保证每折 fall/adl 混合。

## 6. 当前配置与改动清单

### `demo/person_anomaly_config.json`

```json
{
  "confidence": 0.35,
  "track_confidence": 0.15,
  "fall_ratio": 0.9,
  "fall_feature_mode": "bbox",
  "fall_angle_degrees": 60.0,
  "keypoint_confidence": 0.3,
  "fall_seconds": 0.5,
  ...
}
```

- `fall_ratio=0.9` —— 人员框 宽÷高 达到 0.9 就进入倒地计时（站立约 0.4，躺地约 1.6~2.5）。

- `fall_feature_mode` —— `bbox` / `angle` / `auto` / `either` / `both`，实测 `bbox` 最好。
- `track_confidence=0.15` —— 两级门限：已确认轨迹可靠弱检测续命，新轨迹仍需 `confidence`。

**注意：这两个阈值是在 10 段子集上调的，全量上精确率只有 39.6%。没有改成迎合新数据，因为调参解决不了第 5 节的问题，改阈值只会在两种失败之间平移。**

## 8. 下一步

### 优先级 1：引入运动动力学（唯一能解决第 5 节问题的方向）

跌倒 = **快速下降 + 落地后不起**；主动躺下 = 缓慢受控。任何静态姿态特征（宽高比、躯干角）都分不开这两者。

可参考 mfarchan-arm 的状态机设计（只参考思路，该仓库无 LICENSE）：

- 髋部垂直下降速度 `v_y > 0.7 身高/秒`，或躯干角速度 `ω > 120°/秒`
- 状态机：`MONITORING → RAPID_DESCENT → FALL_DETECTED → CONFIRMED_FALL`
- 2 秒内恢复直立 → 判为弯腰/坐下，不报警

关键点数据**已经在缓存里了**（`detect.py` 的 schema 2 存了 17 个关键点），不需要重新推理就能开发和回放验证。

### 优先级 2：实机标定

URFD 是墙上约 1 m 的固定机位；小车摄像头离地很近，透视关系完全不同。**所有阈值必须在实际小车上重新采数据标定**，URFD 的数字不能直接外推。低视角下外框透视畸变更严重，躯干角判据可能反而更有优势（第 3.4 节的结论可能反转）。

### 优先级 3：提升躺地检出覆盖

躺地帧检出率 71.7% 仍是硬上限。可选：用卧姿样本微调检测器；或换 `yolov8s-pose`（74.0%，但 ghost 帧更多）。

## 9. 给后来者的几条提醒

1. **不要从小子集下结论。** 5 个跌倒事件说「80% 检出、零误报」，30 个事件说「53% 检出、36% 的日常段误报」。
2. **不要假设几何上「更好」的特征就会赢。** 躯干角理论上更抗截断和视角，实测 F1 0.142 vs 宽高比 0.791。先测再信。
3. **先修检测覆盖再调阈值。** 检不到人的帧是不可恢复的，任何阈值都救不回来。
4. **帧级召回率不是运营指标。** 按后果拆开漏检（报警前延迟 / 报警后掉线）才有意义。
5. **OpenCV 在含中文的路径下 `imread` 静默返回 None**，import ultralytics 会掩盖这个问题。用 `demo/urfall/detect.py` 里的 `imread_unicode` / `imwrite_unicode`。
